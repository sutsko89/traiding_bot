# Техническое задание: личная торговая платформа

Версия: 1.0 — согласованные продуктовые решения и технические требования.
Дата: 24 ноября 2026 года.
Статус: готово к этапу технической проверки; не является разрешением реальной торговли.
Разработчик: агент Z.ai под контролем владельца.

## 1. Назначение документа

Построить личную расширяемую платформу автоматической торговли на Python + NautilusTrader. Документ охватывает первую версию и будущие возможности. Будущие функции описаны контрактами, ограничениями и условиями приёмки; они не включаются автоматически в ближайший выпуск. Недоступные возможности отключаются явно, а не имитируются заглушками.

Приоритеты владельца, по убыванию:
1. Надёжная автоматическая торговля.
2. Быстрый переход к небольшому реальному депозиту после прохождения защитных проверок.
3. Исследование и сравнение стратегий.
4. Расширяемый фундамент.
5. Удобный интерфейс.

Продукт предназначен только владельцу. Многопользовательский сервис, продажа доступа и управление чужими средствами не входят в целевой объём. Расширяемость не означает обязательства создавать коммерческую платформу.

Нельзя гарантировать прибыль, отсутствие просадки, исполнение стопа по заданной цене или обработку абсолютно всех возможных событий. Обязательны обнаружение неизвестных состояний, запрет необоснованного увеличения риска и диагностируемость.

## 3. Границы и этапы возможностей

### 3.1. Базовый выпуск

Один владелец, Bybit Spot, BTC/USDT, одна активная стратегия, изолированный бюджет. Нужны историческая симуляция, публичная paper-симуляция, доступная тестовая среда и отдельно разрешаемый live. Первая стратегия определяется сравнением простых кандидатов; фиксированная сетка без начального запаса используется как контрольный пример инфраструктуры, но не назначается победителем заранее.

Первый автоматический режим: исполнение утверждённых правил, контроль риска, защитная пауза. Автоподбор новых активов, перераспределение между стратегиями и изменение торговых правил запрещены.

### 3.2. Целевая платформа

Несколько инструментов, стратегий и бирж; общий контроль риска; изолированные бюджеты; исследовательский каталог; автоматизированная оценка режимов рынка; управляемое распределение капитала; выбор активов; сигнальные модели ИИ. Каждый блок вводится отдельным проверяемым этапом.

### 3.3. Исключения

Нет вывода/перевода средств через платформу, займов, спотовой маржи, деривативов в базовом выпуске, высокочастотной торговли, копитрейдинга, самостоятельного изменения кода ботом, обхода риск-контроля моделями. Деривативы допускаются только после отдельного расширения ТЗ и проверки иной модели денег, ликвидаций и позиций. Поля типа рынка в модели не означают готовность торговать этим рынком.

## 4. Архитектурные решения

### 4.1. Структура

Модульный монолит в одном репозитории. Начальные процессы:
- торговый процесс NautilusTrader;
- управляющий FastAPI и минимальная русская панель;
- исследовательские CLI-задачи вне торгового процесса;
- PostgreSQL;
- дополнительные штатные службы движка только если нужны выбранному релизу.

Интерфейс, исследовательские задачи и торговое ядро разделены. Закрытие браузера не прекращает сопровождение заявок. Тяжёлый бэктест не выполняется в торговом цикле. Стратегии не импортируют веб-интерфейс и не обращаются к бирже напрямую.

### 4.2. Владение ответственностью

| Компонент | Обязанность |
|---|---|
| NautilusTrader | Жизненный цикл заявок/исполнений, маршрутизация, штатный cache, исполнение и сверка в пределах возможностей релиза |
| Strategy | Генерирует намерения и принимает торговые события |
| CapitalAllocator | Бюджеты и внутренние резервы |
| RiskPolicy | Независимый допуск и запрет увеличения риска |
| RecoverySupervisor | Барьеры запуска, проверка неопределённости, политика возобновления |
| Accounting | Устойчивые проводки и отчётность по фактическим исполнениям |
| MarketDataQuality | Свежесть, пропуски, корректность данных |
| Research | Версионированные эксперименты и отчёты |
| ControlAPI | Авторизация, команды, чтение проекций |
| UI | Русское представление состояния и подтверждение опасных команд |
| Audit | Журнал решений, изменений и инцидентов |

Не создавать второй независимый OMS поверх NautilusTrader. Прикладные таблицы заявок — проекции/индексы, а не альтернативный исполнитель. Не копировать все типы движка во внутреннюю универсальную оболочку. Зависимость от движка допустима в интеграционном слое и стратегиях, но не в UI.

### 4.3. Источники достоверных данных

| Объект | Источник |
|---|---|
| Факт исполнения/отказа/отмены | Подтверждённые события и отчёты биржи |
| Локальное операционное состояние | Событийное состояние NautilusTrader после сверки |
| Принадлежность стратегии | Устойчивые внутренние идентификаторы и журнал платформы |
| Баланс биржи | Отчёт биржи с временем и признаком актуальности |
| Распределение капитала | Прикладной реестр бюджетов и резервов |
| Конфигурация | Версионируемые утверждённые настройки |
| UI | Только производные представления |

При противоречии нельзя молча назначить удобный источник правым. Создаётся инцидент и блокируется затронутое увеличение риска. Спотовый кошелёк не восстанавливает принадлежность BTC к стратегиям без истории.

## 5. Стек и поставка

- Python: версия по официальной совместимости закреплённого NautilusTrader.
- NautilusTrader: стабильный релиз, lock-файл, отдельная процедура обновления.
- Pydantic для конфигурации и API.
- FastAPI, React + TypeScript + Vite. UI минимален; сервер раздаёт собранную статику, Node.js не нужен в рабочем контуре.
- PostgreSQL для приложения; SQLAlchemy + Alembic владеют только прикладной схемой.
- Штатный backend персистентности NautilusTrader определяется E0. Не предполагать наличие конкретного PostgreSQL-backend в выбранном Python API. Если нужен Redis, проверить его устойчивость, память, восстановление и укладываемость в бюджет.
- Parquet для истории; DuckDB по необходимости исследований.
- uv и зафиксированные зависимости; Ruff, один проверяющий типы инструмент, pytest, Hypothesis.
- GitHub Actions для автоматических проверок без реальных секретов и заявок.
- Основная установка: venv/uv и системные службы. Linux — systemd; локальная Windows — WSL2, если это минимизирует различия окружений. Если нативная Windows официально не поддерживается выбранной комбинацией, это прямо документируется; Docker не навязывать.
- Логи JSON; ротация и ограничения диска. Prometheus/Grafana не обязательны для первой поставки и не должны расходовать бюджет без потребности.

Запрещено автоматическое обновление зависимостей работающей live-системы. Создать install/run/stop/backup/restore инструкции. Контейнеризация возможна позже без смены торговой логики.

## 6. Модель идентичности и конфигурации

Сущности: Venue, Environment, Account, Instrument, Currency, StrategyDefinition, StrategyInstance, CapitalAllocation, Intent, OrderReference, Execution, LedgerEntry, Reservation, Incident, Command, ExperimentRun.

Идентификатор инструмента включает биржу и тип рынка; BTC/USDT сам по себе недостаточен. Аккаунты и ключи paper/test/live строго раздельны.

Минимальные связи:
- намерение принадлежит экземпляру стратегии и версии конфигурации;
- заявка связана с намерением и аккаунтом;
- исполнение связано с биржевой заявкой и уникальным execution ID;
- проводки связаны с исполнением или документированным внешним потоком;
- резерв связан с намерением/заявкой;
- команды и события связаны correlation ID.

Настройки имеют версию, схему валидации, историю изменений и активную утверждённую версию. Секреты не включаются в хеши/экспорты открытых настроек. Изменения проходят предварительную проверку. Критические изменения требуют паузы и повторного допуска. Запрещено менять конфиг файла в обход аудита и ожидать горячей загрузки.

## 7. Модель денег и учёт

### 7.1. Точность

Использовать точные типы движка, Decimal на прикладных границах, NUMERIC в PostgreSQL. В API денежные значения передаются десятичными строками. Float не является источником бухгалтерских остатков. Округление по инструменту явно, пыль сохраняется в учёте.

Каждая сумма содержит валюту. Различать базовую, котируемую, комиссионную и отчётную валюты. Комиссия сохраняется в исходной валюте; оценка в USDT имеет источник, время и признак достоверности. При неизвестной стоимости комиссии отчёт показывает неполноту, а не ноль.

### 7.2. Журнал

Неизменяемый журнал с компенсирующими исправлениями. Для каждой валюты использовать сбалансированные проводки между счетами; сделки связывают движения разных валют, но количества BTC и USDT не складываются друг с другом. Начальная покупка, пыль, комиссии, пополнения и выводы учитываются явно.

Прикладной журнал производен от фактов исполнения и не управляет биржей. Обработка повторов идемпотентна через уникальные ключи и транзакции. Проекция должна восстанавливаться из журнала; неприменимые события сохраняются как инциденты.

Первый метод себестоимости — средневзвешенная стоимость по управляемому пулу, с отдельным аналитическим учётом циклов стратегии. Это не налоговый отчёт. Для будущего нескольких стратегий себестоимость ведётся раздельно по виртуальным портфелям.

### 7.3. Балансы и резервы

Различать биржевой общий/доступный/заблокированный баланс, внутреннее распределение, резерв намерений, нераспределённый остаток. Не вычитать одну биржевую блокировку дважды. В E1 описать точную формулу доступности с учётом возраста отчётов и pending-операций.

Резерв создаётся транзакционно до допуска отправки. Учитывает комиссию и согласованный запас для типа заявки. Не освобождается при неизвестном исходе. Частичное исполнение уменьшает резерв на подтверждённую часть; остаток сохраняется. Все проверки выполняются повторно при фактическом допуске команды, а не только в UI.

### 7.4. Отчётность

Показывать реализованный/нереализованный результат, расходы, equity, экспозицию, drawdown, внешние потоки, отдельный торговый и общий экономический результат. Не вычитать комиссию повторно из уже net-показателя. При изменении внешнего капитала показатели не должны трактовать пополнение как прибыль. Формулы и базы просадки документируются и тестируются.

## 8. Заявки и исполнение

Использовать штатную модель состояний движка и клиентские ID в пределах поддержки адаптера. Поддержать submitted/accepted/partially filled/filled/canceled/rejected/expired и отображаемые состояния unknown/reconciling. Точный mapping закрепить E0.

Требования:
- уникальный client_order_id и устойчивое намерение;
- частичные исполнения и комиссии каждого исполнения;
- отсутствие удвоения при повторах и нарушении порядка сообщений;
- запрос отмены не равен подтверждённой отмене;
- тайм-аут не равен отказу;
- потеря ответа не приводит к слепой повторной отправке;
- после изменения заявки учёт относится к фактической версии/идентичности;
- ручные и неизвестные заявки обнаруживаются, не присваиваются молча;
- массовая отмена ограничена собственными заявками, если аккаунт не выделен.

Не обещать exactly-once между БД и биржей. До отправки подтверждать сохранение намерения и резерва в прикладной БД. В неопределённом окне после аварии проверять движок и биржу; намерение не является разрешением слепо повторить отправку. Не строить два конкурирующих автоматических механизма retry.

Для сетки уровень цены не является уникальным ID обязательства. Исполненная покупка не может потерять продажу из-за занятого уровня. Поддержать отдельные cycle_id или явно проверенное агрегирование с сохранением себестоимости, объёмов и комиссий.

## 9. Политика стратегий и исследований

Первая поставка сравнивает небольшое число простых кандидатов: контрольная сетка без начального запаса, простой трендовый кандидат и отсутствие торговли. Покупка и удержание показывается как дополнительный benchmark. Точные правила кандидатов закрепить до просмотра проверочного результата. Не добавлять индикаторы до получения положительного бэктеста путём бесконечного перебора.

Для каждой стратегии: предпосылка, вход/выход, нужные данные, область применимости, управление открытым активом, ограничения параметров, политика вне диапазона, условия отключения, версия. Неоднозначные правила запрещены.

Разделить подбор, валидацию и отложенную проверку по времени. Исключить look-ahead. Документировать комиссии, спред, задержку, частичные исполнения и ликвидность в пределах модели. На свечах нельзя считать известной точную внутрисвечную последовательность. Проводить чувствительность параметров и расходов, сравнение с простыми вариантами.

Каждый эксперимент хранит commit, lock hash, версию движка/стратегии/настроек, dataset hash, seed, период, предположения и результаты. При одинаковых данных и конфигурации результат совпадает в объявленной точности. Положительный исторический результат не разрешает live автоматически. Стратегия может быть отклонена; платформа не обязана всегда выбирать торговлю.

## 10. Риск

Лимиты: платформа → аккаунт → инструмент → стратегия → операция. Применяются совместно, по наиболее ограничивающему правилу. Проверки до увеличения риска: среда разрешена; спот без leverage/заимствования; инструмент разрешён; данные актуальны; сверка успешна; бюджет/комиссия/округление учтены; частота заявок допустима; нет затронутых unknown-состояний; исполнение не превышает лимиты.

Оба лимита убытка обязательны: от скорректированного выделенного капитала и от корректно рассчитанного максимума equity. Значения владелец утверждает перед live; до этого реальная торговля запрещена. Также обязательны максимальный размер заявки/позиции, число заявок, возраст данных, резерв комиссии, политика slippage и частота команд. Не использовать нули и огромные числа как скрытое отключение лимитов.

Поведение зависит от причины:

| Причина | Новые входы | Существующие заявки/позиция | Возобновление |
|---|---|---|---|
| Ручная пауза | Запрещены | Выходы по утверждённой политике продолжаются | Вручную |
| Лимит убытка | Запрещены | Отменить увеличение риска; закрытие только если заранее разрешено отдельным правилом | Вручную |
| Краткий обрыв | Запрещены до проверки | Сначала установить факты; не объявлять отмену без подтверждения | Автоматически после полной сверки, если нет инцидента |
| Авария процесса | Запрещены | Восстановление и сверка | Первоначально вручную |
| Расхождение/unknown | Затронутый контур заблокирован | Только проверяемые защитные действия | Вручную после разрешения |
| БД недоступна/диск заполнен | Запрещены | Best-effort защитные действия по заранее проверенному плану, журналирование где возможно | После проверки и ручного разрешения |
| Устаревшая цена | Ценозависимые действия запрещены | Работающие биржевые заявки учитываются; отмена по заданной политике | После восстановления и проверок |

Действие «снизить риск» тоже проверяется: устаревшая позиция не даёт права продать произвольный объём. Закрытие позиции может ухудшить результат и не гарантируется при отсутствии связи.

## 11. Состояния и восстановление

Состояния: STOPPED, STARTING, RECOVERING, RECONCILING, READY, ACTIVE, PAUSED, DEGRADED, HALTED. В UI — русские названия и исходный код для диагностики.

Запуск: проверить конфиг/секреты → получить исключительное право исполнения → восстановить состояние движка → загрузить намерения/резервы → подключиться → сверить заявки/исполнения/балансы → обработать пропущенное → разрешить неизвестные исходы → проверить бюджеты и риск → READY → допуск ACTIVE.

Если биржевая история не покрывает простой или сопоставление неоднозначно, запрещено выдумывать данные и автоматически продолжать.

Первоначальное ограничение — один торговый хост и один worker на аккаунт. Использовать системную блокировку и heartbeat/lease для обнаружения второго процесса. Потеря lease запрещает новые отправки; сам lease не объявляется достаточной защитой от split-brain. Active-active и автоматический failover запрещены до отдельного проекта с проверяемым fencing. При смене хоста старый процесс должен быть гарантированно остановлен/лишён ключа.

Проверить crash-окна: до записи намерения, после записи, после передачи движку, после отправки до ответа, после исполнения до записи проекции, во время отмены, во время восстановления.

## 12. Изоляция аккаунта

E0 выясняет доступность субаккаунта, его API-права, spot testnet/demo и соответствие выбранному адаптеру. Возможности testnet и demo не считать взаимозаменяемыми.

Предпочтителен отдельный субаккаунт. Если недоступен — отдельное архитектурное решение и подтверждение владельца до live. Работа рядом с ручной торговлей не разрешается по умолчанию. Автоматически присваивать общий BTC платформе запрещено. Начальные остатки импортируются явной подтверждённой операцией.

## 13. Безопасность

Торговые ключи без вывода/переводов, раздельные ключи сред, ограничение IP при доступности, минимальные права. Секреты вне Git и браузера; локальный файл с правами ОС либо другой проверенный механизм. В логах — маскирование, без тел запросов с секретами. Research не получает live-ключей.

Панель/API по умолчанию только loopback/VPN, авторизация обязательна даже через VPN; защита изменяющих запросов, ограничение частоты входа, безопасные сессии, журнал действий. Критические команды требуют повторного явного подтверждения. Не создавать публичную регистрацию и многопользовательские роли.

Артефакт сборки и зависимости воспроизводимы; автоматическая установка сторонних стратегий и выполнение произвольного кода из панели запрещены.

## 14. Интерфейс и управление

Минималистичный русский интерфейс; статус читается с телефона, без отдельного мобильного приложения. Первая панель: среда, состояние, соединения, свежесть данных, последняя сверка, баланс/equity, бюджет, заявки, исполнения, результат/комиссии, инциденты и команды.

Расширенные разделы: параметры стратегий, результаты исследований, сравнение экспериментов, аудит, настройки. Без декоративных графиков до готовности критических сценариев.

Команды: пауза, возобновление, отмена собственных заявок, остановка стратегии, аварийная остановка, отдельное закрытие позиции. Ответ команды содержит command_id, принятие/отказ, причину, стадию исполнения. Принятие не равно успеху.

На каждом экране заметна среда PAPER/TESTNET/LIVE и время обновления. При разрыве UI не показывает старые значения как актуальные. Ошибки не скрываются всплывающим сообщением без сохранения.

Уведомления — центр инцидентов панели. Email будущий опциональный адаптер, не условие безопасности. Поскольку панель не гарантирует оповещение при закрытом браузере, автономность ограничивается проверенными защитными правилами, а не обещанием немедленно уведомить владельца.

## 15. Эксплуатация без обязательного Docker

Предоставить пошаговые инструкции Windows/WSL2 и Linux. Зафиксировать версии системных зависимостей. Скрипты установки не выполняют live и не меняют API-права.

На VPS использовать systemd, непривилегированного пользователя, корректную остановку, ограниченный restart с возвратом через recovery, ротацию логов, контроль диска и времени. API и торговый процесс разделены, но не получают конкурирующих прав отправки.

До аренды VPS выполнить нагрузочный замер RAM/CPU/диска и рассчитать суммарный ежемесячный бюджет. 1000 рублей — ограничение, не гарантия доступности подходящего сервера. Если бюджет не покрывает измеренные требования, предложить локальную работу или сокращение некритичных служб; не урезать персистентность и риск молча.

Бэктесты на маленьком live-VPS по умолчанию запрещены. Логи и история имеют лимиты хранения. Для базового выпуска предложены ежедневные резервные копии и проверка восстановления перед live; точное расписание, удалённая копия и допустимая потеря данных утверждаются до пилота. Ежедневный backup не заменяет журнал текущих исполнений.

## 16. Будущие возможности: контракты и приёмка

### 16.1. Несколько инструментов

Изоляция состояния по инструментам; общий валютный бюджет не расходуется дважды. Приёмка: BTC и ETH одновременно запрашивают USDT, общий лимит соблюдается; сбой одного инструмента блокирует только допустимый контур.

### 16.2. Несколько стратегий

Вначале виртуальные изолированные бюджеты; все заявки имеют владельца. Противоположные сигналы не приводят к неконтролируемой самоторговле. До общего netting — явная политика конфликтов и принадлежности. Приёмка: повторные исполнения/перезапуски не переносят актив между стратегиями.

### 16.3. Несколько бирж

Матрица возможностей адаптеров, раздельные ключи/лимиты/остатки/сверка. Нет предположения о мгновенном переводе капитала. Приёмка: недоступность одной площадки не инициирует необеспеченную компенсацию на другой.

### 16.4. Адаптивные параметры и переключение

Только внутри утверждённых границ; versioned decision, причина, срок действия, стоимость переключения и cooldown. Открытые обязательства не теряются при смене режима. Приёмка: сравнение с фиксированной базовой стратегией на независимых данных, включая стоимость переключений.

### 16.5. Распределение капитала

Версионированная политика и пределы; нет передачи уже зарезервированных средств. Перераспределение не создаёт скрытые внешние потоки прибыли. Приёмка: конкуренция за капитал, пауза стратегии, частичные исполнения и восстановление.

### 16.6. Автовыбор монет

Только в рамках разрешённой биржи/рынка и явного верхнеуровневого universe. Проверки истории, оборота/ликвидности, спреда, статуса и минимальных заявок; denylist выше рейтинга. Выбор не даёт права немедленно торговать без бюджета и риска. Приёмка: новая/приостановленная/недостаточно ликвидная пара отклоняется; при отсутствии кандидатов — отсутствие торговли.

### 16.7. ИИ

Предварительно целевые роли: сигнал и выбор разрешённых стратегий/параметров. Окончательное решение о внедрении отдельное. Модель не получает секретов и не вызывает биржу. Структурированный ответ, валидатор, TTL, версия модели/промпта/данных, лимит времени/расходов, fallback. Ошибка/отсутствие модели не отменяет сопровождение существующих обязательств. Запрещено обучение и немедленный live-допуск новой модели без независимой проверки. Платные API не обязательны; локальная модель не считается автоматически бесплатной по ресурсам.

## 17. План приёмки

Для каждого теста нужны предусловия, исходные остатки, действия, ожидаемые события, итоговые остатки, артефакты и автоматизация по возможности. Сценарии отказов выполнять в управляемой среде, не на реальных средствах.

| ID | Проверка | Критерий |
|---|---|---|
| T01 | Неверный конфиг | Запуск отклонён с полем и причиной |
| T02 | Live без утверждения/лимитов | Ни одной заявки |
| T03 | Второй worker | Нет второго разрешённого отправителя |
| T04 | Минимум/точность пары | Неверная заявка не отправлена |
| T05 | Комиссия исчерпывает баланс | Нет отрицательного доступного остатка |
| T06 | Повтор исполнения | Одна денежная операция |
| T07 | Частичное исполнение | Остаток/резерв/комиссия согласованы |
| T08 | Тайм-аут создания | Нет слепого повторного ордера |
| T09 | Cancel/fill race | Итог соответствует фактам биржи |
| T10 | Занятый уровень сетки | Выходное обязательство не потеряно |
| T11 | Crash после отправки | Восстановление без необъяснимого дубликата |
| T12 | Исполнение во время простоя | Найдено и учтено один раз |
| T13 | Приватный WS отстал | Нет ложной уверенности в актуальности |
| T14 | Устаревшая цена | Новые зависимые действия запрещены |
| T15 | БД/диск недоступны | Нет нового неучтённого увеличения риска |
| T16 | Ручная заявка/пополнение | Инцидент или явный импорт; не торговая прибыль |
| T17 | Лимиты двух уровней | Стратегия не обходит аккаунтный лимит |
| T18 | Комиссия в третьем активе | Валюта/сумма/оценка сохранены |
| T19 | Аварийная остановка без сети | Нет ложного сообщения об отмене |
| T20 | История недостаточна | Нет автоматического выдуманного восстановления |
| T21 | Детерминированный бэктест | Совпадает в объявленной точности |
| T22 | Будущие данные | Тест обнаруживает look-ahead |
| T23 | Повышенные издержки | Корректный пересчёт, без обещания плюса |
| T24 | Восстановление backup | Рабочая процедура и зафиксированные потери/ограничения |
| T25 | Закрытие UI | Торговое ядро не прекращается |
| T26 | Секреты в логах/сборке | Отсутствуют |
| T27 | Обрыв VPN | Нет потери торгового состояния; доступ корректно ограничен |
| T28 | Перезапуск службы | Сначала recovery, не сразу ACTIVE |
| T29 | Обновление/откат | Нет несовместимого тихого чтения состояния |
| T30 | Проверка капитала 10–20 USDT | Разрешение только реально выполнимой конфигурации |
| T31 | Контроль scope спота | Заём/деривативный инструмент отклонён |
| T32 | Учёт seed-комиссии | Полный портфельный результат согласован |
| T33 | Неизвестный исход дольше окна | HALTED/ручное решение, не бесконечный retry |
| T34 | Отмена собственных заявок | Чужие заявки не затронуты |
| T35 | Повтор команды API | Идемпотентное действие или явный отказ |

Пороговые допуски задаются до тестирования с учётом валют/точности; не подгоняются под ошибочный результат. Прохождение тестов не означает доказанную будущую прибыль.

## 18. Этапы и контрольные ворота

### E0. Проверка технологии — до основной разработки

Закрепить релиз и поддерживаемую среду; проверить Bybit Spot, API-права, субаккаунт, тестовую среду, типы заявок, client IDs, комиссии и историю. Проверить штатный persistence выбранного Python API, реальную семантику flush/recovery и ограничения сверки спота. Выполнить сквозной тест заявки/отмены/исполнения/рестарта. Оценить минимальный капитал и ресурсы. Результат — отчёт пригодности и ADR. Неподдерживаемые возможности не замалчивать. При блокирующем результате остановиться и запросить решение владельца.

### E1. Основание

Репозиторий, CI, конфиги, секреты, типы, схемы, журналы, миграции, процессные границы. Минимальный API/CLI для наблюдения. Нет задачи сначала делать красивый UI.

### E2. Сквозной безопасный сценарий

Одна стратегия → риск/резерв → тестовая заявка → исполнение → учёт → сверка → восстановление. Все типовые crash-окна. Подтвердить отсутствие критической двойной ответственности.

### E3. Сбои и эксплуатация

Пройти критические тесты, резервное восстановление, systemd, VPN, блокировку второго процесса, отчёт ресурсов. Исправить дефекты до расширения.

### E4. Исследование стратегии

Сравнение кандидатов, независимые периоды, расходы, чувствительность, критерии отказа. Выбрать кандидата либо зафиксировать отсутствие основания для торговли.

### E5. Минимальная законченная панель

Русские статусы, балансы, заявки, журнал, подтверждаемые команды. Удобство не должно задерживать исправление критических дефектов.

### E6. Ограниченный live-пилот

Все критические тесты пройдены; нет известных ошибок денег/заявок/восстановления; владелец утвердил лимиты, аккаунт и поведение остановки; капитал 10–20 USDT только при достаточности; ключи минимальны; измеренные расходы в бюджете. Положительный paper за несколько часов не считается достаточным допуском. Критерии длительности/числа событий и проверки стратегии устанавливаются до пилота. Увеличение до 50 USDT только отдельным решением.

### E7–E12. Расширение

Вторая пара → несколько стратегий → распределение → вторая биржа → адаптивность/автовыбор → ИИ. Порядок может пересматриваться владельцем; каждый этап имеет отдельные тесты совместимости и регрессии. Капитал 50 USDT не означает, что все функции следует одновременно включить в live.

## 19. Правила работы агента Z.ai

Перед кодом прочитать ТЗ и репозиторий. Работать малыми этапами: план → изменение → тесты → отчёт → контрольная точка. Не менять фундамент без ADR и согласования владельца. Не создавать целиком будущую платформу одной генерацией.

В каждом отчёте: что реализовано, что не реализовано, команды тестирования, реальные результаты, миграции, ограничения, опасные изменения. Отличать проверенный тест от предположения. Не заявлять о прохождении Bybit-теста без фактического выполнения. Недоступность ключей оформлять как непройденный интеграционный тест, а не эмулировать успех.

Запрещены скрытые fallback на live, заглушки критических проверок, широкие except с игнорированием, финансовые float, автоматическое стирание состояния, сброс БД при recovery, ослабление тестов ради зелёного статуса, размещение секретов в задачах/логах, незапрошенное изменение окружения владельца.
